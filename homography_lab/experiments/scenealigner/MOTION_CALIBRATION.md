# Совместная привязка через движение людей

**MVP реализован и прогнан на камерах 1–3. Он согласует гипотезы камер 1–2, но надёжная абсолютная привязка пока не получена.**
Рабочий трекинг и его глобальные ID не изменены. Контрольные JSON не передаются в расчёт калибровки.

Готовый просмотр: [отчёт пилота](../../reports/motion-office/index.html).
Численные результаты: [RESULTS.md](../../reports/motion-office/RESULTS.md).

## Что реализовано

| Модуль | Назначение |
|---|---|
| `motion_run.py` | Один запуск всего опыта, последовательные стадии, протокол и журналы |
| `motion_frames.py` | Кадры по экранным часам с сохранением исходных PTS; скачки PTS не растягивают движения |
| `motion_observations.py` | YOLO11 Pose, локальные треки тел, признаки OSNet; скрытые стопы не обрывают трек тела |
| `motion_intel_features.py` | Второй независимый дескриптор внешности из существующей модели Intel |
| `motion_floor.py` | Семантика пяти кадров подготовки: уверенные препятствия исключаются, неопределённый пол не объявляется стеной |
| `motion_foreground.py` | Временной фон по девяти кадрам подготовки; неподвижная мебель, ошибочно распознанная человеком, не становится опорой |
| `motion_pairs.py` | Пары по времени/внешности, одинаковые видимые суставы стоп, оценка относительной геометрии и контроль на других эпизодах |
| `motion_geometry_matching.py` | Неоднозначные личности разрешаются общей геометрией пола и взаимно однозначным назначением внутри кадра |
| `motion_body_geometry.py` | Дополнительный опыт: относительная поза по суставам тела и масштаб пола по видимым стопам |
| `motion_candidates.py` | Банк прежних автоматических гипотез и перенос гипотезы между камерами по движению |
| `motion_joint.py` | Совместный выбор гипотез, ограниченное уточнение и отказ при недостаточных доказательствах |
| `motion_evaluate.py` | Только после расчёта: согласованность проекций и отдельная оценка абсолютного места по JSON |
| `motion_report.py` | Изображения и локальный HTML-отчёт |

Нейросети используются готовыми. Обучение новых весов не проводилось; оптимизируются параметры калибровки.
OSNet и Intel используются только для признаков внешности. Межкамерная логика собственная.

## Как работает сопоставление

1. Одна шкала времени строится по сменам секунд экранного счётчика и порядку кадров внутри секунды.
   Доли секунды интерполированы, это не сертифицированная точность физической синхронизации камер.
   Используется прежний, специфичный для этих записей распознаватель OSD; он не читает точки плана.
2. Детектор позы предлагает суставы. Опора допускается при двух уверенных лодыжках либо одной более уверенной;
   отсечения границей кадра, перекрытия другим человеком и уверенные препятствия исключаются.
3. Между двумя камерами сопоставляются **одинаковые видимые суставы**. Если одна видит только левую лодыжку,
   а другая только правую, эти точки не объявляются одним местом. Если видны обе, усреднение выполняется
   после пересечения лучей с плоскостью пола; простое среднее в изображении зависит от ракурса.
   Лодыжки остаются приближением опоры, а не измеренными точками контакта подошв.
4. Признаки внешности сглаживаются по соседним кадрам одного локального трека. Текущие глобальные ID не читаются.
5. Для подготовки относительной геометрии сохраняются несколько вариантов личности при близкой внешности.
   RANSAC ищет общую геометрию; внутри каждого кадра применяется взаимно однозначное назначение.
   Одна пара траекторий/секунда получает один голос, а не десятки голосов от соседних кадров.
6. Для проверки на других эпизодах личности выбираются только по времени и внешности.
   Подогнанная геометрия не выбирает удобные проверочные пары.
7. В обычной ветке относительное преобразование получается между плоскостями пола, восстановленными
   по линзе и вертикали. В дополнительной ветке сначала оценивается относительная поза по суставам тела.
   Суставы головы/плеч не подставляются в гомографию пола. Дополнительная ветка на этих данных отклонена и
   не подменяет основную ветку в итоговом расчёте.
8. Относительная геометрия переносит каждую автоматическую гипотезу места одной камеры в другую.
   Для исходных гипотез проверяется SHA-256 записей: гипотезы от другого видео не принимаются.
9. Для компоненты камер выбирается набор гипотез. Ошибка нормирована через локальные производные проекции:
   уменьшение всей сцены не делает решение лучше только за счёт меньших расстояний на схеме.
10. Уточняются перенос, поворот и масштаб остальных камер; одна автоматическая гипотеза фиксирует систему координат.
    Это фиксация неопределённости, а не подтверждённое место. Перенос ограничен 15 пикселями, поворот — 0.12 рад,
    абсолютное изменение логарифма масштаба — 0.15. Матрицы разных мест не усредняются.

Вариант `motion_joint.py --use-map-motion` дополнительно штрафует прохождение траекторий через стены.
Он оставлен экспериментальным и выключен: текущая схема/маска стен с мебелью давала неверное предпочтение месту.

## Переносимый запуск из ветки Dima_test_lab

Актуальные команды установки, проверки входов и полного запуска приведены в [README лаборатории](../../README.md).
Быстрый пример `python homography_lab/demo.py --output homography_lab/runs/demo-01` воспроизводит геометрию
по сохранённым автоматическим наблюдениям без GPU, весов и исходных записей.
Полный запуск: `motion_run.py --config homography_lab/configs/office-motion.example.json --output ...`.
Используйте новое имя каталога для каждого прогона.

Файлы известных сцен включены в `assets/office`; абсолютные пути прежнего компьютера не нужны.
Пути конфигурации разрешаются относительно JSON. `--video-root`, `--weights-root`, `--hf-cache` и `--pose-weights`
позволяют подключить внешние ресурсы. `--check-inputs` проверяет их до создания результатов.
Проверка по ручным JSON остаётся отдельным вызовом `motion_evaluate.py --reference ...` после расчёта.

## Что считается результатом

`joint-final/joint.json` содержит:

- `components`: связанные компоненты, выбранные гипотезы, альтернативы, причины отказа и проверку на других эпизодах;
- `calibrations`: **диагностические гипотезы**, включая отклонённые; их нельзя автоматически считать рабочими калибровками;
- `absolute_location_verified: false`: движение само по себе не доказывает номер комнаты;
- `automatic_deployment_ready: false`: готовая калибровка для рабочего трекинга не экспортирована.

Статус `abstained` необходимо учитывать при любом дальнейшем подключении. Близкое расположение двух точек на схеме
не означает, что исходные наблюдения относятся к одному человеку: пары также являются предложениями алгоритма.

## Вход для повторного использования ядра

`motion_joint.solve` принимает банк кандидатов и перечень предложенных пар:

```json
{
  "cameras": {
    "cam_1": {
      "probes": [[100, 200], [300, 400]],
      "candidates": [{
        "id": "automatic-candidate-1",
        "unary_cost": 0.0,
        "signature": [[20, 30], [40, 50]],
        "calibration": {
          "camera_size": [2592, 1944], "plan_size": [612, 658],
          "homography": [[1, 0, 0], [0, 1, 0], [0, 0, 1]]
        }
      }]
    }
  }
}
```

Числа примера демонстрируют формат, это не координаты офиса и не конфигурация опыта.
Для гомографии в исправленных координатах обязательно передать `lens` и `homography_input_space`.
Сигнатура — проекции одних и тех же автоматически выбранных проб; она отличает разные места от близких численных вариантов.

Наблюдение хранит камеру, исходное разрешение, время, локальный трек, 17 суставов с уверенностями,
признаки внешности и причину отсутствия опоры. Глобальный ID не нужен.
Адаптер банка кандидатов сейчас привязан к ранее подготовленным пяти камерам этого офиса.
Новый объект потребует нового автоматического банка и распознавания его часов, а не изменения координат в ядре.

## Ограничения текущего MVP

- Обработаны камеры 1–3, пять эпизодов по 25–40 секунд, а не пять полных получасовых записей.
- Кадры 4–5 не обработаны: у 4 другая позиция/шрифт часов; 5 оставлена за пределами начального пилота.
- Камера 3 видит людей иначе; одновременных надёжных наблюдений одинаковых стоп не хватает.
- Переходы между неперекрывающимися камерами по дверям/времени ещё не реализованы.
- Наблюдения других эпизодов не входят в подгонку, но весь пилот использовался при разработке.
  Это инженерная проверка, а не независимый слепой бенчмарк. Старые автоматические гипотезы карты подготовлены ранее по сцене.
- Официальную минуту, установленную организаторами, этот эксперимент не изменяет.
  Итоговое решение для соревнования нужно отдельно проверить в заданном ими временном протоколе.

Следующие необходимые шаги: повысить надёжность пар при похожей одежде, проверить остаточную задержку часов
по независимым событиям, расширить связи камер и добавить отличительные признаки места на плане.
Только после этого имеет смысл подключать калибровки к межкамерному подсчёту.

## Проверки и зависимости

В исходном локальном опыте прошли 71 тест эксперимента и 22 базовых теста. Переносимый набор запускается по README лаборатории. Среди проверок: восстановление относительной геометрии
на синтетической сцене; скрытые/разные лодыжки; одинаковая одежда; неоднозначная абсолютная позиция;
защита от общего уменьшения масштаба; неподвижные объекты; сохранение опорной камеры;
невозможность изменить подгонку заменой проверочных координат; несовпадение SHA-256 видео.

Совместимые добавленные зависимости: `requirements-motion.txt`. Версии фактического прогона записаны в протоколе.
Обновление OpenCV до 5 меняет формат некоторых результатов и нарушало прежние проверки;
поэтому сохранён OpenCV 4.13.0.90 и закреплён Ultralytics 8.3.200. Готовый репозиторий не менялся.

Источники используемых моделей/геометрии:
[YOLO Pose](https://docs.ultralytics.com/tasks/pose/),
[официальные веса YOLO11n Pose](https://github.com/ultralytics/assets/releases/download/v8.3.0/yolo11n-pose.pt),
[OpenCV: относительная поза и проективная геометрия](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html).
